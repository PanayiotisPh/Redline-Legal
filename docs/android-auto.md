# Android Auto

Tripper appears on an Android Auto head unit as a template app: live
distance, speed, duration and peak G, with one Start/Stop button.

## How it fits together

The car UI is **native Kotlin, not React Native**. Android Auto renders
Google's own templates from a `CarAppService`; none of the app's screens can
be reused there. The car service runs in the same process as the RN app but
has no access to React state, so the two talk through a shared object:

```
lib/androidAuto.ts  ──push telemetry──▶  TripperCarBridge  ──▶  TripperCarScreen
       ▲                                  (Kotlin object)          (car display)
       └──────────── Start/Stop command ──────┘
```

- `plugins/androidAuto/kotlin/TripperCarBridge.kt` — the shared state. Plain
  singleton, deliberately not React-aware: the car screen can exist while the
  RN activity does not.
- `TripperCarScreen.kt` — the `PaneTemplate` shown in the car.
- `TripperCarAppService.kt` — what the car host binds to.
- `TripperCarModule.kt` — the RN native module.
- `plugins/withAndroidAuto.js` — the config plugin that wires all of the
  above into the generated `android/` project.

**The car never starts recording itself.** A tap sends a command up to JS,
which performs the same `handleToggle` the phone button does. That keeps GPS
and sensor access in one place, keeps the save-on-stop flow intact, and
preserves the privacy rule that a trip only ever begins from an explicit user
action.

### Why a config plugin

`android/` is regenerated by `expo prebuild`, so nothing there can be edited
by hand — it is wiped on the next run. The plugin re-applies the Kotlin
sources, resources, manifest entries, gradle dependency and package
registration every time.

**After changing anything under `plugins/androidAuto/`, re-run
`npx expo prebuild --platform android` before building**, or the old copy
stays in `android/`.

## Testing on a PC (Desktop Head Unit)

You do not need a car. The DHU runs the Android Auto interface on your
desktop against the phone over ADB.

### One-time setup

1. **Install the DHU**: Android Studio → SDK Manager → *SDK Tools* tab →
   check **Android Auto Desktop Head Unit Emulator** → Apply. It installs to
   `%LOCALAPPDATA%\Android\Sdk\extras\google\auto\`.

2. **Install Android Auto on the phone** from the Play Store (pre-installed
   on most modern Android phones).

3. **Enable developer mode in Android Auto**: open the Android Auto settings
   on the phone, scroll to the bottom, tap **Version** ten times until it
   confirms developer mode. Then in its overflow menu → *Developer settings*
   → enable **Unknown sources**, which is what allows a sideloaded debug app
   to appear.

### Each session

```bash
# 1. Start the head unit server on the phone
adb forward tcp:5277 tcp:5277

# 2. Launch the DHU
cd %LOCALAPPDATA%\Android\Sdk\extras\google\auto
desktop-head-unit.exe
```

Tripper should appear in the DHU's app launcher. If it does not, see below.

## Troubleshooting

**App missing from the launcher.** Nearly always *Unknown sources* not being
enabled in Android Auto's developer settings. Verify the service is
registered at all with:

```bash
adb shell dumpsys package com.panayiotisph.tripper | grep TripperCarAppService
```

**"Open Tripper on your phone" on the car screen.** Expected when the RN app
has never been launched — the recorder engine does not exist yet, so Start
would have nothing to drive. Open the app once on the phone.

**Values not updating.** The screen throttles to one refresh per second by
design; the car host drops updates that arrive faster, and a driver cannot
read a number changing ten times a second anyway.

## Shipping

Android Auto apps require **Google Play review against the Driver
Distraction guidelines**, and the declared category
(`androidx.car.app.category.POI`) is what they review against. Development and
DHU testing need no approval; distribution does.

Do not switch the category to `NAVIGATION` without reason — that category
expects turn-by-turn guidance, which Tripper does not provide, and it carries
the strictest review.

## Known gaps

- **No map in the car.** POI template apps cannot draw a map surface; that
  needs the navigation category. The car screen is stats and a button.
- **Untested on real hardware.** Verified to compile, install, and register
  its service; the DHU is the next step, a physical head unit after that.
- **CarPlay is not implemented.** It needs macOS to build and an Apple
  entitlement granted by application, neither of which is available here.
